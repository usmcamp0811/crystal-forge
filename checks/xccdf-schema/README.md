# XCCDF Schema Check

This check validates both the vendored NIST XCCDF 1.2 schema and the
repository's `cf-xccdf-1` extension schema (`schemas/cf-xccdf-1/`) against a
set of hand-authored and writer-generated XML fixtures, using `xmllint` and
OpenSCAP.

## What it verifies

- A comprehensive hand-authored XCCDF 1.2 `Benchmark` fixture (status,
  title, description, version, `cf:bundle` metadata, profiles with
  selections, groups, and rules with checks/fixes/idents/references)
  validates against the vendored XCCDF 1.2 XSD.
- Individual CF extension fixtures — `cf:policy` with
  `require-crystal-forge-agent`, `cf:policy` with `custom-check`, and
  `cf:policy-identity` — validate against the CF extension XSD
  (`schemas/cf-xccdf-1/cf-xccdf-1.xsd`) in isolation.
- A full hand-authored document that embeds CF extension elements inside
  `Rule` `metadata` (the XCCDF extension point) validates against the XCCDF
  1.2 schema as a complete document, proving the extension placement itself
  is schema-legal.
- The actual `xccdf-export-fixture` binary output — generated by the same
  `write_bundle_xccdf_export()` function the API endpoint uses, not a
  hand-written approximation — validates against XCCDF 1.2, and its
  `check-content/policy` element count is asserted directly. Each CF
  extension node type extracted from that real writer output (`bundle`,
  `policy-identity`, `policy`, `source-mappings`, `opaque-xml`) is also
  independently validated against the CF extension schema.
- OpenSCAP's own XCCDF 1.2 parser (`oscap xccdf validate`, `oscap info`)
  accepts both the hand-authored comprehensive fixture and the real writer
  output, catching schema issues `xmllint` alone might miss.

## Why it is a separate check

XCCDF/CF-XCCDF export correctness is a data-interchange contract with
external tooling (OpenSCAP and any downstream XCCDF consumer). Validating
it against two independent validators (`xmllint` schema validation and
OpenSCAP's own parser), against both synthetic fixtures and the real writer
output, belongs in its own focused, fast, non-VM check rather than inside a
browser-driven integration test.

## Run it

```sh
nix build .#checks.x86_64-linux.xccdf-schema --print-build-logs
```

No VM is involved. The `xccdf-export-fixture` binary comes from the core
server build (`cf-server-core-drv`), which keeps the builder, keygen, and
web UI closures out of this check.

## Out of scope

- This does not exercise the API endpoint that serves an XCCDF export over
  HTTP, authentication, or authorization around export — only the writer
  function's output shape and schema conformance.

## CI

Not present in the `.gitlab-ci.yml` `flake-check` matrix by name; it runs as
part of a broader `nix flake check` where applicable.
